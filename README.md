# Football — 美式足球（NFL）比賽預測工具

一套專業的 NFL 比賽預測工具，核心是 **Elo 戰力評等**，並疊加 **休息天數／短週賽、先發QB異動、
比賽天氣、分區內對戰、季後賽情境** 等會實際影響比賽結果的因素，透過邏輯迴歸／線性迴歸整合成
一套「進階整合模型」。所有方法論公開透明、可回測，並誠實列出與真實 Vegas 收盤盤口的準確度比較。

**線上網站（GitHub Pages）**：戰力排名、本週／整季預測、互動式對戰預測器、模型準確度公開頁 —
見下方「GitHub Pages 網站」章節。

只使用 Python 標準函式庫 + numpy，不需要任何其他第三方套件即可運作。

內建資料為 **真實歷史賽事**：1999 年至今（含目前進行中的賽季，以及已公布的完整未來賽程）共 7000+
場已完賽的 NFL 常規賽與季後賽，以及該賽季所有已公布的未來賽程，取自公開的
[nflverse/nfldata](https://github.com/nflverse/nfldata) 專案，內容包含比分、休息天數、天氣、
先發QB、教練、以及 Vegas 收盤盤口（分差／美式賠率）。已將搬遷過的球隊（如 OAK→LV、SD→LAC、
STL→LA）統一為現行代碼，讓 Elo 歷史連續不中斷。所有 32 支球隊皆附有正體中文隊名（見下方對照表）。

### 盤口資料是真實的嗎？

是。`spread_line` / `home_moneyline` / `away_moneyline` / `total_line` 等欄位是 nflverse/nfldata
官方資料字典（`nflreadr::dictionary_schedules`，[來源](https://raw.githubusercontent.com/nflverse/nflreadr/master/data-raw/dictionary_schedules.csv)）
明確定義的**真實歷史收盤盤口**（"Odds for home/away team to win the game" / "The spread line for
the game"），不是模擬或虛構數據。開發時也另外做了獨立驗證：抽查歷史上懸殊的比賽（例如 2013年
DEN vs JAX，DEN 主場美式賠率 -5000、JAX 客場 +2173），確認 `spread_line` 的正負號與方向、與該場
比賽實際的大幅懸殊賠率完全吻合（大幅領先的一方對應大幅有利的賠率與盤口），並且抽查了 2026 年已
公布的未來賽程盤口，同樣可對應到已知的真實對戰強弱關係。`market` 回測（見下方）就是直接用這些
真實盤口計算準確率，而非用模型自己的預測結果假裝是「市場」。

### 比賽賽程／日期時間是真實的嗎？

是。除了資料源頭本身（nflverse/nfldata）就是被廣泛使用、持續在真實比賽日更新的社群維護資料集之外，
開發時另外對 2026 年賽程做了結構性驗證，這種程度的規律性幾乎不可能來自虛構或隨機資料：

- **賽制完全符合現行 NFL 規則**：2026 年例行賽共 272 場（32 隊 × 17 場 ÷ 2）、橫跨 18 週，
  每一隊「剛好」都打 17 場、「剛好」都只有 1 週輪空（bye week），且沒有任何一隊在同一週被排了
  兩場比賽 —— 這是 NFL 自 2021 年賽季起採用的官方賽制（18 週制、每隊 17 場），資料完全吻合。
- **開賽時段完全符合 NFL 真實轉播慣例**：週日比賽的開賽時間集中在 13:00（早場）、16:05／16:25
  （午後場）、20:20（週日夜賽 Sunday Night Football）美東時間；另外有 6 場週日 09:30 美東時間
  的比賽 —— 這正是 NFL 近年海外系列賽（倫敦／德國／巴西）為配合當地時段所安排的早晨開賽時間。
  週四夜賽（Thursday Night Football）與週一夜賽（Monday Night Football）也都各自穩定地每週
  出現一場，與真實轉播慣例完全一致。
- **內部一致性**：全部 7000+ 筆資料的 `gameday`（日期）與 `weekday`（星期幾）欄位逐筆核對，
  零筆不一致。

以上檢查腳本可在 `scripts/` 目錄外自行執行（見資料集本身的 `season, week, gameday, weekday,
gametime` 欄位）。**已知限制**：本開發環境的對外網路僅允許連線到少數程式碼託管網域（例如
GitHub），無法連線 ESPN、NFL.com、Wikipedia 等網站做即時第三方交叉比對，因此以上驗證是基於
資料本身的內部結構一致性與已知的 NFL 賽制/轉播規則，而非直接比對另一個獨立來源。若你想更進一步
確認，可自行到 nfl.com 或 ESPN 的官方賽程頁面，抽查幾場比賽的日期與時間是否與網站上顯示的相符。

## 三種模型（含結合真實賠率的整合預測）

| 模型 | 說明 | CLI 參數 |
| --- | --- | --- |
| `elo` | 純 Elo 評等基準模型（538 NFL Elo 方法論） | `--model elo` |
| `advanced`（預設） | Elo 評等 + 休息天數 + 先發QB異動 + 天氣 + 分區／季後賽情境，透過邏輯迴歸／線性迴歸整合 | `--model advanced` |
| `blend` | 把 `advanced` 模型的判斷跟**真實 Vegas 盤口**結合成單一「整合預測」 | `backtest --model blend`（`predict`/`train` 不適用，見下方說明） |

`blend` 跟前兩者不太一樣：它不是獨立訓練的模型，而是把 `advanced` 模型的勝率／預測分差，跟真實市場
賠率（美式賠率換算出的隱含勝率、以及收盤讓分）依固定權重混合出的最終判斷，只在有真實盤口資料的比賽
才能算（歷史回測、以及已公布盤口的未來賽程）。所以 `predict`／`train` 沒有 `--model blend` 選項 —
任意兩隊的假設對戰沒有真實盤口可以結合。

### 進階模型考慮的因素

- **Elo 戰力評等**：逐場更新，內建勝分差修正（大勝/大敗調整幅度更大）、主場優勢加成（預設 48 分）、
  季後賽權重提升（預設 ×1.2）、賽季間回歸平均值（預設 1/3）。
- **休息天數差（rest_diff）**：主客兩隊的休息天數差，反映短週四夜賽的疲勞劣勢、待命週後的體能優勢。
- **先發QB異動**：追蹤每隊最近已知的先發QB，偵測是否臨時更換 — 這是單場比賽結果最大的擺動因子之一，
  且對於未來賽程也能用官方已公布的預期先發QB提前判斷。
- **天氣與場地**：戶外比賽的低溫（≤0°C）、強風（≥15mph）條件；室內／圓頂球場不受影響。
- **分區內對戰／季後賽情境**：分區對手較熟悉彼此、季後賽強度與變異度不同。
- **市場賠率校驗**：使用真實歷史 Vegas 收盤盤口（分差與美式賠率）作為**獨立比較基準**（不是模型輸入），
  確保評估公正透明。此外也額外提供 `blend` 整合預測，把 `advanced` 模型跟真實盤口混合成單一判斷 —
  混合權重怎麼選出來的，見下方「參數是怎麼選出來的？」。

不包含的因素（超出目前資料來源範圍）：即時傷兵名單細節、比賽當下即時天氣預報（僅使用比賽日已知的
歷史/預報氣象資料）、教練臨場戰術調整、球員層級進階數據（如 EPA/CPOE）。這些都是可以在未來擴充的方向，
詳見下方「已知限制」。

## 使用方式

### 1. 訓練模型（`train`）

```bash
nflpredict train --model advanced          # 預設，寫入 ratings_advanced.json
nflpredict train --model elo               # 純 Elo 基準模型，寫入 ratings.json
```

輸出範例（advanced）：

```
[advanced] trained on 7278 games (1999-2026)
  training accuracy : 64.7%
  training log loss : 0.6277
  spread MAE        : 10.51 points
  avg total points  : 44.3
  feature weights (standardized logistic regression coefficients):
    elo_diff        +0.697
    rest_diff       +0.061
    div_game        -0.047
    qb_change_home  -0.132
    qb_change_away  +0.109
    cold_game       +0.040
    windy_game      -0.013
    playoff         +0.005
```

可調整的 Elo 參數：`--k`（K因子，預設20）、`--home-advantage`（主場加成，預設48）、
`--playoff-boost`（季後賽K因子倍率，預設1.2）、`--revert`（賽季間回歸平均值比例，預設**0.45**，
見下方「參數如何選出來的」）。

### 2. 預測比賽（`predict`）

```bash
nflpredict predict --home KC --away BUF
```

```
[advanced] Buffalo Bills (BUF) @ Kansas City Chiefs (KC)  [home field]
------------------------------------------------------------
  Elo ratings        : KC: 1488.4   BUF: 1601.0
  Win probability    : KC: 43.4%   BUF: 56.6%
  Predicted score    : KC 21.1 - 23.1 BUF
  Predicted margin   : KC -2.0
  Favorite           : Buffalo Bills
  Context factors    : (none — default/neutral context)
```

`advanced` 模型可用旗標描述比賽情境（用於「若⋯會如何」的假設情境分析）：

```bash
nflpredict predict --home KC --away BUF \
  --div --away-qb-change --home-rest 10 --away-rest 4
```

支援旗標：`--neutral`（中立場地）、`--div`（分區內對戰）、`--playoff`（季後賽）、
`--home-rest N` / `--away-rest N`（休息天數，預設7）、`--home-qb-change` / `--away-qb-change`
（先發QB臨時異動）、`--cold`（低溫戶外比賽）、`--windy`（強風戶外比賽）。加上 `--json`
可輸出機器可讀格式。

### 3. 查看戰力排名（`ratings`）

```bash
nflpredict ratings --top 10
```

### 4. 回測驗證準確度（`backtest`）

用「隨時間往前走」(walk-forward) 的方式驗證模型：每場比賽先用當下已知的評等/模型做預測、記錄結果，
再更新評等，避免用到未來資訊（look-ahead bias）。`advanced` 模型每個賽季開打前只用先前賽季的資料
重新校準一次迴歸係數，同樣不會偷看未來。

```bash
nflpredict backtest --start-season 2015 --model all
```

```
backtest: seasons >= 2015
  [elo] 3061 games
      winner accuracy : 63.9%
      Brier score     : 0.2214  (lower is better, 0.25 = coin flip)
      spread MAE      : 10.22 points
  [advanced] 3061 games
      winner accuracy : 64.4%
      Brier score     : 0.2208  (lower is better, 0.25 = coin flip)
      spread MAE      : 10.20 points
  [market] 3060 games
      winner accuracy : 66.1%
      Brier score     : 0.2118  (lower is better, 0.25 = coin flip)
      spread MAE      : 9.83 points
  [blend] 3060 games
      winner accuracy : 66.1%
      Brier score     : 0.2119  (lower is better, 0.25 = coin flip)
      spread MAE      : 9.83 points
```

`market` 是同期真實 Vegas 收盤盤口的表現，作為誠實的對照基準：長期穩定打敗收盤盤口本身就是眾所皆知
的難題，這裡如實呈現而非誇大宣稱「打敗莊家」。`blend` 是把 `advanced` 模型跟真實盤口混合出的整合
預測（見下方「參數是怎麼選出來的？」），可以看到它的數字跟 `market` 非常接近 — 這是刻意且誠實的
結果，不是巧合。

### 5. 匯出網站資料（`export-site`）

```bash
nflpredict export-site --start-season 2015
```

重新訓練 elo / advanced 兩個模型、跑三方回測比較，並將戰力排名、整季賽程預測、模型準確度、以及給
瀏覽器端互動預測器使用的模型快照，全部寫入 `docs/data.json`（GitHub Pages 網站讀取的資料檔）；
同時也會把逐場的時序回測明細（見下方「歷史回測紀錄」）寫入 `docs/backtest_history.json`。

## GitHub Pages 網站

`docs/` 目錄是一個純靜態網站（HTML/CSS/JS，無需建置工具），內容包含：

- **互動式對戰預測器**：任選兩隊、開關情境因子（主客場、分區戰、季後賽、QB異動、天氣、休息天數），
  瀏覽器端即時運算勝率與預測比分（與後端訓練用的是同一套模型參數）。
- **本週／整季預測**：目前已公布賽程的每一場比賽，含勝率、預測比分、預測分差、真實市場**讓分**
  （傳統讓分盤格式，例如 `BUF -7 / LAC +7`），以及結合真實賠率算出的**整合預測**，同時顯示美東
  時間與台灣時間的實際開賽日期時間。每場比賽最上方另有一行**「本場推薦」**，會自動比較「不讓分」
  （猜贏家）跟「讓分」（猜誰能贏過盤口分差）兩種推薦各自的信心，信心較高的那一種會顯示出來（見
  下方「`讓分` vs `不讓分`：怎麼決定要推薦哪一種？」）。
- **本週串關推薦**：從當週「本場推薦」信心最高（≥60%）的比賽中，自動挑出最不容易爆冷門的 3 場
  湊成一組串關（全部要猜中才算贏），信心不夠高的比賽不到 3 場時會誠實顯示「暫不建議」而非硬湊
  （見下方「`串關`是怎麼湊出來的？」）。
- **戰力排名**：目前 Elo 評等排序。
- **模型準確度與市場比較**：公開的回測結果，`elo` / `advanced` / `market` / `blend` 四方比較，
  外加「智慧推薦」策略本身的誠實回測數字（選了幾次讓分／不讓分、各自命中率、整體命中率），以及
  「本週串關推薦」策略本身過去的真實命中率。
- **歷史回測紀錄**：可手動載入、逐場列出的時序回測明細（非事後諸葛）— 每場比賽當時 Elo／進階模型／
  市場盤口／整合預測，四方各自的賽前判斷，以及實際比分與對錯，外加「智慧推薦」欄顯示當時選了哪一種
  推薦、信心多少、猜不猜得中，可依賽季與「猜對/猜錯/爆冷」篩選、翻頁瀏覽。
- **手動更新按鈕**：不必等到每天自動更新，可直接在頁面上（或連到 GitHub Actions 頁面）立即觸發
  重新抓資料＋重新訓練＋重新發佈。
- **方法論頁**：列出模型考慮的所有因素與已知限制。

### 啟用方式（一次性設定）

此 repo 的 GitHub Pages 尚未啟用，需要 repo 擁有者手動開啟一次：

1. 到 repo 的 **Settings → Pages**
2. **Source** 選擇 `Deploy from a branch`
3. **Branch** 選 `main`，資料夾選 `/docs`，按下 **Save**
4. 幾分鐘後網站會發佈在 `https://<你的帳號>.github.io/<repo名稱>/`

> **注意大小寫**：GitHub Pages 的網址路徑必須跟 repo 名稱的**大小寫完全一致**（GitHub API 呼叫不
> 分大小寫，但 Pages 網址是分大小寫的）。這個 repo 實際名稱是 `Football`（大寫 F），所以正確網址是
> `https://<你的帳號>.github.io/Football/`，不是全小寫的 `football`。若打開網址出現 404，先檢查
> 網址的大小寫是否跟 repo 名稱一致；也可以直接到 **Settings → Pages** 頁面複製上面顯示的網址，
> 那個一定是正確的。

啟用後，`.github/workflows/update-predictions.yml` 會自動：每天 UTC 10:00（= 台灣時間每天晚上
18:00）重新抓取最新真實比賽資料、重新訓練模型、重新產生 `docs/data.json` 與
`docs/backtest_history.json`，並自動 commit + push — 網站內容會持續保持在最新戰績與賽程之上，
不需要手動維護。

### 網頁上的「手動更新資料」按鈕

網站首頁最下方有一個手動更新區塊，提供兩種立即觸發更新的方式：

1. **最簡單**：直接點連結前往 GitHub Actions 頁面，按「Run workflow」。不需要任何額外設定。
2. **網頁上一鍵觸發**：因為 GitHub Pages 是純靜態網站、沒有後端伺服器，若要從網頁本身直接呼叫
   GitHub API 觸發 workflow，需要一組有權限的 GitHub 權杖（personal access token）。設定方式：
   - 到 GitHub **Settings → Developer settings → Fine-grained tokens → Generate new token**
   - **Repository access** 選擇「Only select repositories」→ 選這個 repo
   - **Permissions** 只勾選 **Actions: Read and write**（不需要其他任何權限）
   - 產生後把權杖貼到網站的輸入框，按「觸發更新」

   權杖只會存在**你自己瀏覽器的 localStorage**（下次造訪同一台裝置/瀏覽器時會自動沿用，不用重貼），
   不會被送到 GitHub API 以外的任何地方，也不會被寫進這個 repo。但仍建議：只給最小權限（僅這個
   repo 的 Actions 讀寫）、不要在公用電腦上長期保留，並在用完後按「清除已儲存的權杖」。

## 使用自己的資料

`train` / `backtest` / `export-site` 接受任何符合以下欄位的 CSV（`data/nfl_games.csv` 的欄位）：

```
season, week, game_type, gameday, home_team, away_team, home_score, away_score,
home_rest, away_rest, div_game, roof, surface, temp, wind,
home_qb_id, away_qb_id, home_qb_name, away_qb_name, home_coach, away_coach,
spread_line, home_moneyline, away_moneyline, total_line
```

只有 `season`、`home_team`、`away_team`、`home_score`、`away_score` 是必要欄位（未賽的比賽把分數
留空即可，會被視為未來賽程），其餘欄位缺漏時會使用預設值 / 不觸發該項情境因子。`game_type` 非
`REG` 者會被視為季後賽。想更新為最新資料，執行 `python3 scripts/fetch_data.py`。

## 執行測試

pip install -r requirements.txt

## 參數是怎麼選出來的？

Elo 的 K因子、主場加成、季後賽倍率、賽季間回歸平均值，以及進階模型的迴歸正規化強度
（`l2_logit` / `l2_linear`），並不是憑感覺挑的，而是做過一次網格搜尋，並用「調參／驗證」
兩個獨立時間區間避免自欺欺人（在調參區間選出來的參數，如果沒辦法在完全沒看過的驗證區間
也表現得一樣好，就代表只是湊巧套中雜訊，不能採用）：

- **調參區間**：2010–2020 賽季（用時序回測，Brier score 越低越好）
- **驗證區間**：2021 年以後（調參時完全沒用到，只用來確認調參區間選出的參數是否只是巧合）

搜尋結果：
- `revert_to_mean`（賽季間回歸平均值）從原本的 1/3 調成 **0.45**：在調參區間穩定變好
  （Brier 0.2187 → 0.2184），驗證區間也確實同方向變好（0.2237 → 0.2236），雖然幅度不大，
  但兩個獨立區間都一致，判斷是真實訊號而採用。
- K因子、主場加成、季後賽倍率：搜尋過合理範圍後，都沒有找到能穩定贏過現有預設值（源自
  538 NFL Elo 方法論）的組合，維持原樣。
- 進階模型的 `l2_logit` / `l2_linear` 正規化強度：搜尋 0.25～8 的範圍，Brier score 幾乎沒有
  變化 — 因為 `elo_diff` 這個特徵的權重遠大於其他情境特徵，合理範圍內的正規化強弱對結果影響
  很小，維持原預設值 2.0。

誠實說明：以上調整幅度都很小（小數點第三、四位），不是「原本很不準、調完變超準」的戲劇性
結果，而是在已經合理的方法論基礎上做嚴謹驗證，確認目前參數沒有明顯可改善的空間。

### `blend` 整合預測的混合權重是怎麼定的？

同樣用「調參（2010–2020）／驗證（2021年以後）」的兩段式做法，這次搜尋的是「`advanced` 模型
的判斷要佔多少權重」（勝率用 log-odds 空間的加權平均，也就是邏輯迴歸常用的「logistic pooling」；
預測分差用一般加權平均）。搜尋範圍是 0%～100%，每 5% 一格：

- **調參區間最佳值**：模型權重 5%（也就是 95% 權重在真實盤口）
- **驗證區間最佳值**：模型權重 0%（也就是完全採用真實盤口，不混入模型）
- 完整曲線很清楚：只要給自己的模型超過約 10–15% 的權重，兩個區間的 Brier score 都會開始變差；
  權重越高、變差越多（權重 100% 純模型時，驗證區間 Brier 從 0.2114 惡化到 0.2230）。

**誠實結論**：資料很清楚地顯示，混入我們自己的模型並不會讓預測比真實盤口更準 —— 真實市場本身
就很難打敗（賠率背後有傷兵報告等我們模型沒有的資訊）。目前 `blend` 採用模型權重 **10%**，這是
一個刻意保守、貼近搜尋最佳值、但仍保留一點自己模型判斷的設定，而不是宣稱「混合之後打敗了市場」。
在網站與 CLI 上，`blend` 的數字理應會非常接近、但通常不會優於 `market` 那一列，這是預期中、
且誠實揭露的結果。

### `讓分` vs `不讓分`：怎麼決定要推薦哪一種？

每場比賽其實可以下兩種不同的注：「不讓分」（單純猜誰贏）跟「讓分」（猜誰能贏過盤口分差，也就是
及格分差 ATS）。這兩種賭法的信心不必然一樣高，所以網站與回測都會自動比較兩者、選信心較高的
那一種當作「本場推薦」：

- **不讓分信心**：`整合預測`（`blend`）勝率離 50% 有多遠（例如 74% 獲勝機率 → 信心 74%）。
- **讓分信心**：把「整合預測分差」減去「真實盤口分差」得到一個「模型跟盤口差多少」的差值，再用
  歷史上這個差值實際對上比賽結果的誤差標準差（只用當時已發生過的比賽，時序回測、無偷看未來），
  換算成一個常態分布下「贏過盤口」的機率。誤差樣本不足 20 場時（例如資料剛開始累積），讓分信心
  留白，直接以不讓分推薦為準。
- 兩者之中信心較高的即為「本場推薦」，並清楚標示是哪一種、信心多少 — 不管選哪一種，另一種的數字
  仍然照常顯示在同一張卡片／同一列裡，不會被藏起來。

**誠實回測結果**（2015 年至今、共 3060 場有完整盤口資料的比賽）：這套「自動選信心較高者」的策略
絕大多數時候（約 98%）還是選「不讓分」，只有約 2%（62 場）的比賽讓分信心真的贏過不讓分信心。而且
這少數被選中的「讓分」推薦命中率（約 53%）明顯低於「不讓分」推薦的命中率（約 66%）—— 這正好印證
了讓分盤本來就是設計成接近五五波的難題，模型很難穩定地找到「贏過盤口分差」的邊。誠實說：這個功能
提供的是「有憑有據地在兩種賭法之間自動選擇」，而不是「找到了必勝的讓分秘訣」。

### `串關`是怎麼湊出來的？

每一週把所有已經算出「本場推薦」信心的比賽，依信心高低排序，只挑信心 ≥60% 的比賽，取信心最高的
前 3 場湊成一組串關（`DEFAULT_PARLAY_LEGS` / `DEFAULT_PARLAY_MIN_CONFIDENCE`，見
`advanced_model.py`）。串關要全部 3 場都猜中才算贏，所以顯示的「全部命中機率」是把 3 場的信心
直接相乘（假設每場比賽互相獨立 — 這是簡化假設，實際上同一週的比賽可能有天氣系統等共通因素，網站
上也誠實註明了這點）。如果這週信心夠高的比賽不到 3 場，就直接顯示「暫不建議」，不會硬湊信心不足
的比賽進去湊數。

**誠實回測結果**（2015 年至今、共 239 週）：有 211 週湊得出一組完整的 3 場串關，其中真正 3 場
全部命中的有 113 週，命中率約 **53.6%**（事前用信心值相乘估計的平均命中機率約 49.9%，跟實際命中
率相當接近，代表信心值本身的校準沒有明顯偏差）。誠實說：這個命中率已經比任何單一場比賽的推薦都
低很多（單場「智慧推薦」命中率約 66%），這正是串關「一場沒中全組泡湯」的本質 — 這個功能提供的是
「用一致的規則挑出最有信心的組合」，而不是「找到了穩賺不賠的串關公式」。

### 有沒有再繼續優化模型？

在完成上面的串關功能之外，也額外做了兩項誠實的優化嘗試，結果都記錄在這裡（而不是悄悄略過）：

- **正則化強度（L2）網格搜尋**：`advanced` 模型的邏輯迴歸／線性迴歸正則化強度過去從未調過（固定
  用 2.0）。用 0.5～16.0 的網格重新搜尋，結果：**幾乎沒有影響**（Brier score 變化小於 0.0001）。
  這是預期中的結果 —— 特徵數量少（8 個）、訓練樣本數多（7000+ 場），迴歸本身已經穩定，正則化強度
  在這個範圍內不是有效的調整旋鈕。維持原本的 2.0 不變。
- **加入「近期戰績」特徵**：嘗試在既有特徵之外，加入「主客兩隊最近 N 場比賽的平均勝分差」（滾動
  視窗，一樣是時序、無偷看未來），測試 N = 3／4／5／6／8／10 場。用同樣的「調參（2010–2020）／
  驗證（2021 年以後）」流程檢驗：調參區間有極小幅改善（Brier 改善約 0.0003，幾乎可忽略），但驗證
  區間的結果不穩定（不同 N 之間互有優劣、有些反而變差），**沒有一致的改善**。這很可能是因為 Elo
  評等本身（尤其是勝分差加權更新機制）已經把「近期戰績」的資訊吸收進評等裡了，額外加一個近期戰績
  特徵大多是重複資訊。因此沒有把這個特徵加入正式模型。

誠實結論：目前這套方法論（Elo + 情境特徵的邏輯/線性迴歸）大概已經在「可用資料能給出的準確度」附近
碰到天花板 —— 要再進一步提升勝率，可能需要更細緻的輸入資料（例如即時傷兵名單、逐次進攻數據），而
不是再調整現有參數或加類似的統計特徵。

## 模型說明與已知限制

- 這是一個**戰績與可量化情境因子驅動**的統計模型；不包含即時傷兵名單細節、臨場天氣預報（僅用比賽日
  已知資料）、教練臨場調度、球員層級進階數據（EPA/CPOE等）。若要進一步提升準確度，可以把這些訊號
  另外整合進特徵向量。
- Elo 只反映「球隊整體實力的相對強弱」，預測比分是由評等差與情境特徵的迴歸結果換算而來，屬於統計估計，
  實際比分變異度遠大於模型給出的期望值。
- 情境特徵刻意只用連續型的 `rest_diff`，而不是額外疊加「短週賽」二元旗標：測試時發現兩者高度共線，
  會讓迴歸係數方向不穩定（甚至反直覺地翻轉），單一連續特徵反而更穩健。
- 誠實的基準比較：同期真實 Vegas 收盤盤口的勝負準確率通常會略優於本模型 —
  這是公開的統計事實（市場資訊包含了傷兵報告等本模型沒有的內部資訊），不代表模型無效，而是展示
  一套嚴謹、可回測、方法論公開透明的框架，讓使用者能自行判斷模型的可信度。
- 本工具目的為研究、分析與教育用途，**不構成博弈建議**。
